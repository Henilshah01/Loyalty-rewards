# Assumptions

The brief leaves many gaps. Each one is listed with the choice made and why. Items marked
**(tunable)** can be changed through environment variables without touching code.

## Proof of purchase

1. **A unique code inside each box is the proof of purchase.** The factory does not see retail sales and
   has no point-of-sale integration, so the only thing it controls is what it puts in the box. Knowing a
   code means the customer has the physical box in hand. *Alternative rejected:* receipt photos – needs
   manual review or OCR, easy to fake, and a heavy workload for the owner.
2. **The code sits under a flap or scratch panel** inside the box so it cannot be read in a shop.
   This is a packaging decision for the client; the software works either way.The same applies to the QR label: it contains the code, so anyone who can scan it can claim the points.
3. **Codes are generated by the owner in batches** (one per production/print run). Right after generation the owner can print QR labels (up to 500) or download a CSV for the printer; the CSV includes the QR link for each code.
4. **Format `XXXX-XXXX-XXXX-XXXX`:** 12 random characters (60 bits) + 4 checksum characters generated using a secret-keyed checksum (HMAC). Crockford Base32 (no I, L, O, U) makes codes easier to read and type. Look-alike characters are automatically corrected (O→0, I/L→1).
5. **The plaintext code is shown once** at generation, then only a keyed hash is stored. If the owner
   loses the CSV the codes cannot be recovered – they would void the batch and print a new one. This is
   the price of a database leak not exposing usable codes.

## Fraud and reuse

6. **One code = one claim by one account, forever.** No transfers, no "un-claiming".
7. **Lockout (tunable):** 5 failed attempts within a rolling 15-minute window lock the account for 15 minutes. Typos count too – the checksum makes honest typos rare, and the lock is short.
8. **Daily cap (tunable):** at most 20 successful claims per account per 24 hours. A household might
   open several boxes in a day, but not hundreds.
9. **Per-IP request limits** on all API routes (120/min), sign-in (10/min) and claims (20/min).
10. **Email is not verified in the MVP.** Sending email adds a provider and a deliverability problem.
    Fake accounts are not blocked, but each still faces the lockout and daily cap, and the Security tab
    flags several accounts on one IP. *Production fix:* email verification and/or phone OTP.
11. **Stolen or mis-printed stock** is handled by voiding the batch: every unclaimed code stops working
    immediately. Codes already claimed stay claimed (the owner can suspend the account).
12. **Insider risk is out of scope:** someone with access to the CSV or the printer can use the codes.
    The audit trail (who claimed what, when, from which IP) helps investigate afterwards.

## Rewards

13. **Rewards are fulfilled manually** (merchandise, vouchers, experiences). A customer's request
    deducts the points immediately and creates a *pending* request; the owner marks it *fulfilled* or
    *rejected*. Rejection refunds the points and returns the stock.
14. **Points are a single balance with no expiry, tiers or multipliers.** Points per code are set per
    batch and frozen at creation (changing a later batch never alters printed boxes).
15. **Stock is optional** per reward (blank = unlimited). Out-of-stock rewards cannot be requested.
16. **Delivery details are a free-text note** on the request; no address book or shipping integration.

## People and access

17. **Two roles only:** customer and owner (`admin`). The owner account is created by the seed script
    from environment variables; public sign-up can only ever create customers.
18. **Suspended customers** keep their points but cannot sign in, claim or redeem.
19. **Sessions:** JWT (7 days), signed and verified on the backend, stored in browser storage. Simple for an MVP; production should use secure httpOnly cookies and refresh tokens.

## Technical

20. **No multi-document transactions in the MVP.** The application is designed to work with a standalone MongoDB instance, which does not support multi-document transactions. Critical operations use atomic conditional updates and compensating actions if a later step fails. These compensating actions can also fail, so reconciliation is a documented production improvement (see ARCHITECTURE.md). A replica-set deployment could support transactions in a future version.
21. **Rate limiter is in memory,** so it is per server process. Fine for one instance; use Redis if scaled out.
22. **Scale target:** Designed for thousands of customers and up to 10,000 codes per batch request. This is a design target, not a verified performance benchmark.
23. **Claim attempts are kept for 90 days** (automatic expiry), then deleted.
24. **English only, no notifications.** Customers see request status in the app; the owner contacts them.
25. **Single factory / single brand.** No multi-tenant support.
